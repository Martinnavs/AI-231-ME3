Topic A: WebRTC AEC3 internals, SpeexDSP, and which bindings expose which settings. Look at the actual WebRTC source (webrtc.googlesource.com/src, modules/audio_processing/aec3/, api/audio/echo_canceller3_config.h, modules/audio_processing/audio_processing_impl.cc), the webrtc-audio-processing repository packaged for PipeWire/PulseAudio (gitlab.freedesktop.org/pulseaudio/webrtc-audio-processing), PipeWire's module-echo-cancel docs/source, SpeexDSP source/docs, and the LiveKit Python SDK (github.com/livekit/python-sdks, livekit-rtc package) and its Rust side (livekit/rust-sdks, webrtc-sys).

A1. AEC3's internal delay estimator uses matched filters on 4x-downsampled audio; defaults EchoCanceller3Config.delay.num_filters = 5 and a matched-filter length of 32 blocks of 4 ms; together these cover about 640 ms of render-to-capture delay. (Give the real default values of delay.down_sampling_factor, delay.num_filters, the matched filter length / window and alignment-related fields, and the resulting maximum delay AEC3 can find. If the 640 ms figure is wrong, give the correct one and how it is computed.)
A2. In AEC3, set_stream_delay_ms() only provides an initial offset that is ignored once the internal delay estimator locks; delay.use_external_delay_estimator defaults to false. (What does AudioProcessing::set_stream_delay_ms actually do in current code when AEC3 is the echo controller? Is the value used at all? Does a hint far from the real delay hurt?)
A3. AEC3's render buffer allows at most kMaxApiCallJitterBlocks = 30 blocks (120 ms) of render calls ahead of capture calls; feeding more render frames in a burst before the next capture call triggers a "render overrun" (BufferingEvent::kRenderOverrun) that flushes the buffer and resets delay estimation. (Find the real constant name(s) and value(s), e.g. delay.api_call_jitter_blocks, and what happens on overrun/underrun.)
A4. AEC3 handles clock drift by stepping its bulk delay one 4 ms block at a time with hysteresis (hysteresis_limit_blocks = 1, delay_headroom_samples); its main adaptive filter is about 12 blocks (48 ms) long by default. (Give real default filter lengths for the refined/main and coarse/shadow filters, and anything documented about clock drift handling, e.g. a ClockdriftDetector.)
A5. AEC3's nonlinear suppressor (SuppressionGain) uses separate "normal_tuning" and "nearend_tuning" masks and a dominant near-end detector (dominant_nearend_detection with fields such as enr_threshold, hold_duration) that must see near-end energy exceed residual echo for several blocks before relaxing suppression; the first 100-250 ms of a barge-in can therefore be suppressed. (Confirm the config fields and their defaults; find any source that documents or measures onset damage during double-talk.)
A6. AEC3 can export its linear-filter output before nonlinear suppression (e.g. a "linear AEC output" / export_linear_aec_output option, EchoControl::SetCaptureOutputUsage). (Confirm the exact names, which version added them, and whether webrtc-audio-processing 1.x or 2.x exposes them.)
A7. livekit.rtc.AudioProcessingModule exposes only four booleans (echo_cancellation, noise_suppression, high_pass_filter, auto_gain_control) plus process_stream, process_reverse_stream and set_stream_delay_ms, and no EchoCanceller3Config fields or linear output. (Check the current livekit-rtc Python source and its version; list exactly what it exposes. Does it use AEC3 or the mobile AECM?)
A8. PipeWire's module-echo-cancel with the webrtc method wraps webrtc-audio-processing (AEC3 in 1.x) and exposes webrtc.* options in aec.args; when the sink and source are on different clocks PipeWire adaptively resamples to lock them before feeding the canceller. (List the real aec.args webrtc options; confirm or refute the clock-matching claim.)
A9. SpeexDSP: speex_echo_cancellation() is a purely linear MDF adaptive filter and its residual echo suppression happens only in the preprocessor (speex_preprocess_run with SPEEX_PREPROCESS_SET_ECHO_STATE); the documentation says capture and playback must share one clock and 50-100 ppm of drift prevents convergence. Also: "it removes about 10-18 dB of linear echo". (Confirm what the Speex manual says about clocks/drift and delay; any published ERLE number.)
A10. Python bindings: webrtc_audio_processing on PyPI (xiongyihui) is unmaintained and wraps an old WebRTC (AEC2, around M50); webrtc-noise-gain (rhasspy) wraps webrtc-audio-processing 1.x but only for noise suppression and gain. (Give last release dates. Also list any maintained Python binding that exposes AEC3 configuration or the linear output; and any maintained Python binding for SpeexDSP echo cancellation, with last release date.)
