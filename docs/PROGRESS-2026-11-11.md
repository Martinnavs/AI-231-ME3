## 3. Endpoint silence (0.7 s default): what is and is not known

Replay of `out/calibration-baseline.wav` (continuous speech, no video) through `scripts/try_stt.py --wav ... --vad-hold 6 --tail 4` against a private `lan_speech` server, three runs per setting: at 0.7 s the server ended the turn at the first pause of 0.7 s or more and the final came 1.15-1.20 s after speech stopped; at 1.2 s the clip stayed one turn (no pause that long). So the setting works and removes 0.5 s of waiting by construction. **Not known:** whether 0.7 s splits a user's mid-sentence pause into two turns, and whether it reduces spurious video turns. The A/B in the "Open" section of `docs/HEADSET-MIC.md` (new recordings, both microphones, three runs per cell) is still the test and needs the owner. If a rehearsal shows split turns, restart the speech server with `--endpoint-silence 1.2`.

## 27. STT and TTS as MCP tools on the Pi (2026-11-13)

The course requires STT and TTS as MCP services. Streaming speech stays direct (`lan_speech` over websockets: a stdio MCP call per utterance would add latency and cannot stream), so the requirement is met by a thin wrapper, not a reimplementation: the existing speech MCP server (`voice_agent/mcp_servers/speech.py`: three tools, path and size hardening, 40 tests) gets a `lan` backend (`src/audio_engine/lan.py`, 100 lines) that talks to the laptop's speech server (ws `/stt`, ws `/tts`, GET `/voices`, Bearer token). Options `--lan-url` and `--lan-token-file` (the token file's path, never the token, goes on the command line: MCP children do not inherit the environment). No streaming, retries or reconnects.

The Pi agent starts it as an optional server when `SPEECH_LAN_URL` is set (`pi_service.sh agent` sets it to the laptop's speech port; `agent_tools.speech_command`); its three tools (`transcribe_audio_file`, `synthesize_speech_to_file`, `get_tts_voices`) are in `MODEL_HIDDEN`, so the model never sees them (an anti-pattern for the live path, but they exist and work). The 0.4 s settle after the last audio in the transcriber is needed because the server sends no reply to `finalize` when a pause already ended the utterance; verified against the real server (3 of 3 transcripts of a clip, text identical).

Checked on the Pi after `make pi-sync` (commit `114fc47`): the agent runs the speech child with the `lan` backends, and `scripts/speech_mcp_check.py` (speak a sentence to a WAV through the MCP server, transcribe it back) returned `voices: 8  tts: 0.42 s  stt: 1.25 s`, text exact; on the laptop 0.37 s and 0.82 s (one run each).
